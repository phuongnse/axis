# Axis UI System

## Goal

Make every Axis surface derive from one product-level UI constitution. Components implement semantic roles; they never become independent sources of visual or interaction policy.

## Hard gates

Follow [reference.md](../reference.md).
- Non-trivial entry work **Requires** current `$axis-design-gate` evidence.
- UI conformance is a specialization of [docs/PLATFORM_STRATEGY.md § Enterprise Production Baseline](../../../docs/PLATFORM_STRATEGY.md#enterprise-production-baseline). Preserve the caller's project-level production-fitness decisions and evidence; never infer overall production readiness from the UI profile, frontend gates, or visual acceptance alone.
- Apply the sign-off and provenance rules from [docs/playbooks/frontend.md § Component design](../../../docs/playbooks/frontend.md#component-design); do not broaden or weaken them here.
- `frontend/ui-coverage-profile.json` owns the versioned requirement set, evidence kinds, representative modes, and invalidation triggers; its requirement count is not a universal sufficiency claim. `frontend/ui-foundation.json` is the strict lifecycle plus contract/evidence manifest for defined-or-later contracts and must classify every profile requirement exactly once as covered, gap, or explicitly allowed not-applicable. Covered entries trace to real acceptance-test ids, matching evidence-sidecar rows, declared evidence, and required modes. Only entries whose state is `enforced`, have no gaps, have accepted review and perceptual state, and whose id appears in the checked `enforcedContracts` registry belong to the enforced-contract union. `frontend/src/lib/ui-foundation.ts` owns the finite typed consumer mapping and derives that union from the registry, while `frontend/src/lib/active-surface-registry.ts` owns real owner/implementation symbols. Keep the profile, manifest, and both typed registries aligned; filename/path lists, prose, screenshots, automated checks, or approval cannot establish conformance by themselves.
- A new or replaced cross-feature visual language or surface archetype is incomplete until its owner, contract evidence, active consumers, and deterministic conformance policy land together. Do not keep a draft owner, legacy composition, or unverified consumer on the supported path.
- Do not refresh the baseline merely to silence unexplained drift or discard existing exception evidence.
- Run owned checks directly; unresolved verification command selection **Delegates** to `$axis-script-scope`.

## Inputs

- Requested UI change, current design phase, and [docs/playbooks/frontend.md § Component design](../../../docs/playbooks/frontend.md#component-design) contract.
- User task, read/edit mode, content roles, hierarchy, relationships, and responsive/accessibility expectations for a new or changed view.
- Representative routes and complete applicable states and modes from the current UI coverage profile, including light/dark, desktop/compact, pointer/keyboard, reduced motion, localization, screen-reader semantics, and zoom/reflow.
- Applicable page-archetype foundations, including [Collection Page](../../../docs/foundations/data-display/collection-page.md) and [Managed Dialog](../../../docs/foundations/overlays/managed-dialog.md).
- Registry config/source, baseline, affected consumers/tests, and provider diff.
- Design Gate and sign-off evidence when triggered.

## Workflow

1. Declare exactly one review unit before implementation: constitution/foundation, one surface owner, or one consumer of an unchanged enforced owner. Choose the largest coherent boundary that has one owner, contract, invalidation set, and review decision; default to the whole foundation/surface or a complete consumer. Do not split one owner into typography, spacing, individual regions, or other implementation details merely to make the unit smaller. Split only where ownership, acceptance, verification, or safe rollback is genuinely independent, and record that boundary rationale in the Design Gate. Classify constitution definition, surface-contract definition, verified enforcement, localized composition, theme, registry sync, exception, or provider/style replacement. Do not bundle the next independently owned review unit.
2. Inventory representative surfaces before proposing code. Define product-level semantic roles across color, typography, spacing, density, radius, elevation, iconography, motion, layering, layout, responsive behavior, accessibility, feedback, and interaction state. Keep exact reusable values in `theme/axis-theme.json`, project consumer-facing roles through the generated typed `axisStyles` contract, and keep product-neutral behavior in the visual-system contract. Do not define policy by enumerating components, class names, CSS properties, or DOM symptoms.
3. Keep authenticated resource management table-first through [Collection Page](../../../docs/foundations/data-display/collection-page.md): one primary data table launches create, view, and edit work into app-scoped managed windows. Reserve alert dialogs for bounded confirmation and dedicated workbench routes for workflows that meet the foundation's complex-layout exception.
4. Changing durable visual guidance **Requires** `$axis-doc-hygiene`: update the visual-system contract, profile, and semantic theme only where each owns the decision; link from consumers and remove superseded guidance. Before JSX, complete the Design Gate for the declared review unit, record semantic-role, hierarchy, anatomy, state, responsive, accessibility, clean-cutover, stop-condition, and profile requirement/evidence matrices, and obtain required project-owner authorization. Authorization approves the unit's scope, not its rendered result or the next unit.
5. Consume [docs/playbooks/client-experience.md](../../../docs/playbooks/client-experience.md); confirm mode, relationships, vocabulary ownership, semantic component mapping, and every badge, tag, card, border, icon, and heading has one distinct job.
6. Implement only the declared unit, then run `python scripts/axis.py check ui-foundation`, `python scripts/axis.py check theme`, `python scripts/axis.py check ui-baseline`, and `python scripts/axis.py frontend ci`. Inspect typed catalog/real-symbol registry diffs plus rendered markers and evidence. Confirm authored code consumes `axisStyles`; the AST guard may prevent raw semantic-utility bypass but cannot define a role or prove conformance. Use `rg` only for bounded discovery or a one-time retirement sweep; never make filename or source-text patterns the durable proof of ownership. Compare equivalent semantic roles across overlays, navigation, collections, forms, and feedback instead of comparing component names.
7. Choose one source owner per decision: the visual-system contract owns invariants, the theme owns reusable values, upstream primitives own mechanics, app patterns and finite surface contracts map roles to reusable composition, and features own product state plus relationships inside declared semantic slots. Define a surface API by capability, not implementation terms: keep leaf content inside owner-rendered anatomy; represent any region with its own states, relationships, or actions as a typed semantic model rendered by the owner; never use generic JSX as subsystem anatomy. Let type and parser-backed boundaries prove that ownership, and let component/browser tests prove contract outcomes. A component-specific test may prove a mapping but cannot create a new convention.
8. For a cross-feature definition, add one finite shared contract owner at manifest state `defined`, pending acceptance, its foundation spec, current component/browser evidence, and an exact honest partition of the current profile in `frontend/ui-foundation.json`; keep perceptual status `missing` until version-controlled comparisons exist. Every covered entry must name owning acceptance ids and sidecar-declared evidence, while unproved requirements remain gaps. Add the surface id and active consumers to the typed catalog and bind real owner/implementation symbols in the registry. Require the compatible typed surface id in the owner's semantic API, keep feature/route imports out through the parser-backed module rule, and emit contract/id markers at the rendered owner boundary. Prove applicable product states and every required profile mode. Do not infer adoption from filenames, direct-import text, matching markup, or a generic standards claim.
9. Generate perceptual artifacts only after deterministic and runtime checks pass. Record new or changed artifacts as `candidate`, present the exact review unit and canonical mode matrix to the project owner, and stop before another unit. The agent and automated checker cannot convert candidate evidence to accepted evidence. If the project owner requests a change, keep acceptance pending, implement only that feedback within the same unit, rerun invalidated gates, and present a new candidate.
10. After explicit project-owner acceptance, record the current acceptance state and move the manifest from `defined` to `verified` only when the profile has no gaps and every covered requirement has current acceptance, evidence-kind, mode, accessibility, standards-assessment, responsive, and accepted perceptual proof as applicable. A passing checker proves trace integrity, not WCAG/ISO compliance or perceptual adequacy. Approval provenance stays in the task or pull request, not durable guidance. Move to `enforced` only after typecheck proves every active registration and real-symbol mapping, rendered evidence confirms owner composition, retirement evidence is declared, retired compositions are removed, and deterministic policy passes. The registry is an ownership/evidence map, not a screen-design catalog: a new consumer of an unchanged enforced owner needs typed registration and product-state evidence, while a profile, shared-owner, constitution, theme, evidence, acceptance, or consumer change reopens the requirements named by the profile invalidation map. Requested and authorized work stays task-local; revising an enforced contract returns to `authorized`, then `defined` with pending acceptance during replacement.
11. For registry work, run the dependency-risk gate, preview and diff only the named component family through the Axis shadcn wrapper, and refresh `frontend/ui-baseline.json` only with established provenance while preserving approved exceptions.
12. Name required evidence: review unit, workflow and acceptance state, owning standards/constitution/profile/theme, contract owner, registered consumers, archetype and semantic audit, applicable state/mode matrices, exact covered/gap/not-applicable partition, acceptance/evidence traces, component/browser/candidate-or-accepted visual evidence, criterion-level standards assessment when claimed, baseline, frontend quality, retirement sweep, and registry diff when applicable. Run owned checks directly and use the verification handoff only when command selection remains unresolved.

Keep machine lifecycle detail in the manifest, but report one human-facing roll-up for the review unit: `In progress` while implementation or non-review evidence is incomplete, `Awaiting review` when the candidate and technical gates are ready and only project-owner review remains, and `Complete` only after acceptance and the unit's intended verified/enforced target is satisfied. Requested changes return the same unit to `In progress`. Do not make the project owner reconcile raw lifecycle, acceptance, and perceptual states unless an audit or discrepancy requires them.

## Stop conditions

Stop the current unit and return to its Design Gate when the owner is unclear, a new semantic role or exception appears, scope reaches another foundation/owner/consumer, a required gate fails, a baseline changes unexpectedly, the project owner changes the requirement, or an accepted standard/profile/constitution/theme/owner/evidence/consumer assumption changes. Apply the profile's invalidation map. Do not refresh evidence, weaken a gate, classify an unproved requirement as covered, make an unsupported standards claim, or begin the next unit to work around the stop.

## Output

Lead with the single human-facing review-unit roll-up and decision needed. Keep workflow state, profile version, contract owner, registered consumers, archetype and semantic decisions, applicable state/mode matrices, exact coverage partition, acceptance/evidence traces, component/browser/visual/standards evidence, provenance/diff, baseline, invalidated requirements, retirement sweep, and unresolved exceptions or provider leakage available as audit detail rather than presenting three independent status strings as the primary result.
