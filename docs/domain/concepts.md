# Axis concepts

This is the vocabulary used in code, APIs, configuration files and UI. Use these terms, and link a
concept's reference page for its detail. The **From** column gives the milestone that introduces the
concept (see the [roadmap](../roadmap.md)). The docs sweep at milestone close checks this column and
moves a concept to a later milestone when it was not delivered, see
[the life of a milestone](../delivery.md#the-life-of-a-milestone).

## Packaging and lifecycle

These concepts say what an application is made of and how it becomes a running release.

| Concept | Meaning | From |
| --- | --- | --- |
| **Application** | A deployable business application. It is a folder of resources with a manifest, and owns a set of sites. | M1 |
| **Resource** | One typed configuration item with a stable `id`, a `kind`, a `name`, a format version and typed references to other resources. | M1 |
| **Module** | A reusable, versioned folder of resources with a `module.json` manifest. Applications declare the modules they use with version ranges. Each application gets its own copy of a module's entities, sequences and seeds. A module can list the modules it depends on, and the application resolves the graph flat. Modules hold processes, pages, policies, triggers and scenarios, call connectors through connector slots and name resources of their dependencies. See [modules](../reference/modules-and-templates.md#modules). | M8, M20 (processes, pages, policies, triggers, connector slots, dependencies), M24 (scenarios) |
| **Role slot** | A role that a module names without knowing the application's roles. `module.json` declares its slots, module policies and task assignees name them, and each application maps every slot to one of its own roles. See [modules](../reference/modules-and-templates.md#processes-pages-policies-and-dependencies). | M20 |
| **Connector slot** | A connector that a module names without knowing the application's connectors. `module.json` declares each slot with the operations and typed fields the module needs, module processes call it, and each application maps every slot to one of its own connectors, which must match the operations and types. The bindings stay with the application's connector. See [modules](../reference/modules-and-templates.md#processes-pages-policies-and-dependencies). | M20 |
| **Built-in module** | A module that Axis maintains and ships with the installation, under `modules/` in the repository, such as `approvals`: a standard process that a business builds its application from instead of starting from scratch. It is configuration, not platform code, and has its own SemVer version. See [D102](../decisions/d102-built-in-modules-open-to-change-and-bound-by-a-contract.md) and [built-in modules](../reference/built-in-modules.md). | M26 |
| **Module contract** | What a module guarantees whatever an application changes: the lifecycle of its entities, with guarded transitions, its core validations, the effects of a transition, a grant ceiling for each role slot, and its contract scenarios. The engine checks it on every write. An application may turn off one named point with a `relax` entry and a reason, which marks its release off-standard. Platform invariants never relax. See [module contracts](../reference/module-contracts.md). | M24 |
| **Customization layer** | An application's changes to a module, as files under `customizations/<module id>/` that name the module's resources and elements by name and hold only what changes. Compilation applies it to the pinned module version, and an upgrade merges it three ways. Ejecting a module copies it into the application instead, which ends its upgrades and its contract. See [customization layers](../reference/customization-layers.md). | M25, M29 (upgrades and eject) |
| **List key** | The property by which a customization layer finds an element of a list, ignoring letter case: `name` for most lists, `field` for a form section's fields and a data source's `groupBy`, and `id` for seed records. A layer's element with a key the module's list has changes that element, and one with a key it lacks is added. See [list keys](../reference/customization-layers.md#list-keys). | M25 |
| **Application template** | An installed, versioned application folder with a `template.json`. Studio creates a new application by copying it, with new resource ids, the new name and a site path that follows the name. See [application templates](../reference/modules-and-templates.md#application-templates). | M11 |
| **Release** | The immutable compiled form of an application at one point in time. It pins every resource version it uses. New work starts on the active release. Running work, with its tasks, forms, texts and package versions, stays on its release until it ends, while roles and policies come from the active release. | M1 (basic), M6 (full) |
| **Diagnostic** | A validation or compile error or warning. It points at the resource, field and path that caused it. | M1 |
| **Studio** | The visual editor of an application's resources. It edits the JSON files of the application folders that `Studio:Folders` lists, through an authoring API, and creates applications in `Studio:ApplicationsPath`. Its edit routes never activate a release: it asks for an activation through a **publish request**. It shows where each resource is used. Pages, forms and processes have visual designers on the Design tab of their editors, and a page or a form opens on its Design tab. See [Studio](../reference/studio.md) and the [authoring API](../reference/authoring.md). | M8, M13 (page and form designers), M14 (process designer) |
| **Publish request** | A request that Studio stores in the tenant database to validate or publish an application, to activate a release of its history, back to an older one or forward to a newer one, or to run the application's test scenarios. It holds a snapshot of the folder, or a release id, and has a status: `queued`, `running`, `succeeded` or `failed`. A separate publisher runs it, so the server never activates a release itself. A publish can target the tenant's **preview tenant**. See [publishing](../reference/authoring.md#publishing). | M10 |
| **Release history** | The per-tenant list of activations of each application. Each row holds the release, its content hash, the actor, the label, the note and the request. A release gets a number, 1, 2, 3…, the first time it is activated in the tenant. A request to activate a release names one from it. See [release history](../reference/storage.md#release-history). | M10 |
| **Reference index** | The uses and used-by edges between resources, text keys, extension packages and modules. A compile builds it in memory, and it is not stored in the release. Studio shows it as a **Uses** list and a **Used by** list. See [reference index](../reference/configuration.md#reference-index). | M8 |

## Data

These concepts describe the records an application keeps and how it reads and changes them.

| Concept | Meaning | From |
| --- | --- | --- |
| **Entity** | A business record type. Each entity becomes a typed PostgreSQL table in the tenant database. | M1 |
| **Field** | A typed attribute of an entity, with constraints. | M1 |
| **Sensitive field** | A field marked `"sensitive": true`. Inspection hides its value, and the value is stored encrypted under a data key of its tenant. A sensitive field cannot be filtered, sorted, aggregated or indexed, except through an exact lookup that a field may declare. See [data encryption](../reference/data-encryption.md). | M7 (hidden in inspection), M27 (encrypted at rest, exact lookup) |
| **Computed field** | A field whose value comes from an expression over the record's own fields and its child rows. It is stored and recomputed on every write. A release or a migration that changes it recomputes the stored values, and a large table is recomputed in batches by the worker while reads that need the field wait or are refused. See [recomputing computed fields](../reference/migrations.md#recomputing-computed-fields). | M2 |
| **Data source** | A named, parameterized query over entities. It declares projections, filters, sorting, paging, related entities and aggregates. Pages, widgets, rules and processes read data only through data sources or entity APIs. See [data sources](../reference/data-sources.md). | M2 |
| **Sequence** | A `sequence` resource that hands out business numbers from a format such as `PR-{yyyy}-{n:5}`, giving `PR-2026-00042`. A `text` field names it and gets its number on create, in the create's transaction, so there are no gaps. When the format has a year, the counter restarts each year in the application time zone. See [sequences](../reference/resource-files.md#sequences). | M3 |
| **Seed data** | Reference or demo records shipped with an application and applied idempotently. Seed data is not created by process code. A seed can be synced, so that changed values update the seeded records on start. | M1 (basic), M2 |
| **File** | A file that a `file` field holds: uploaded first as `pending`, then attached by a record write, downloaded by id under the owner record's read grants, and stored where the application's `storage` binding says. See [file fields](../reference/file-fields.md). | M15 |
| **Import and export** | Writing the rows of a data source or an entity to a CSV or spreadsheet file, and creating or updating records from one. Each needs its own grant action, `export` or `import`. An export runs the rows query under the user's read grants. An import runs on the worker, checks every row in a dry run, then writes all rows or none through the record command. See [import and export](../reference/import-export.md). | M15 |
| **Migration** | A `migration` resource that changes one entity's stored data in a way that is not additive: rename or drop a field, drop the entity, fill nulls or convert values. Activation runs it once per tenant, before additive provisioning, in the same transaction. A destructive migration is refused while running work pinned to an older release uses the column. See [migrations](../reference/migrations.md#migrations). | M6 |

**Field types** are text, integer, decimal, boolean, date, date-time, enum (with a label for each
value), reference (to another entity), references (a set of records, many-to-many), child collection
(owned rows such as line items, which the record API reads and writes through the owner record),
money (with a fixed currency or a currency field) and file.

**Field constraints** are required, unique, `maxLength` and `minLength` on text, precision and scale
on decimal, and `min` and `max` on integer, decimal, date and date-time. The server checks the
ranges and the database does not, so changing one needs no migration. A field may also have a default
value and be searchable, and an entity declares its indexes, while the platform adds one on every
reference and owner column. See
[entity field types and constraints](../reference/resource-files.md#entity-field-types-and-constraints).

## Logic

These concepts are the logic of an application: what it computes and what it does.

| Concept | Meaning | From |
| --- | --- | --- |
| **Expression** | A typed, side-effect-free formula in Axis's [expression language](../reference/expressions.md), checked at compile time. | M2 |
| **Rule** | A named, reusable expression with declared typed parameters and a result type. Validations, data source filters, process conditions and policy filters call rules. | M2 |
| **Operation** | A typed unit of work with declared inputs, outputs, capabilities and idempotency, for example "create record", "send email" or "call the purchasing system". Operations are built in or come from extension packages. The built-in `updateRecord` sets fields of the subject record inside the step's transaction. The built-in `callConnector` calls one operation of a connector outside the step's transaction, with a stable operation identity as its idempotency key, see [connector calls](../reference/process-execution.md#connector-calls). Package operations, named `<package>/<operation>`, run staged outside the step's transaction, like `callConnector`, and a context limits them to the capabilities they declare, see [package operations](../reference/process-execution.md#package-operations). | M3 (basic), M5 |
| **Extension package** | A .NET class library with a SemVer version that adds typed operations under declared capabilities. It references only `Axis.Extensions` and ships with a manifest, `axis-package.json`. Packages are installed per installation, and each version loads in its own `AssemblyLoadContext`. An application declares the packages it uses with version ranges, and its releases pin the exact versions. Process steps run their operations, an operation context hands out only the declared capabilities, and calls are retried under the step's retry policy. A package is trusted code, not sandboxed. Its operations run in package runners, and it can hold custom widgets. See [extension packages](../reference/extension-packages.md). | M5, M21 (runners), M22 (widgets) |
| **Package runner** | A process of the `Axis.PackageHost` host that runs the operations of one installed package version, outside the worker, with an empty environment and one network route. Each runner runs one call at a time and serves every tenant. See [package runners](../reference/extension-packages.md#package-runners). | M21 |

## Processes

These concepts describe durable work: processes, the people who take part and the commands that fix
what the engine cannot finish alone.

| Concept | Meaning | From |
| --- | --- | --- |
| **Process** | A versioned definition of steps and transitions, executed durably. It explicitly declares the entities it works on. A process names one entity, its subject, and runs for one record of it, or has no subject and takes typed parameters, see [processes without a subject](../reference/process-flow.md#processes-without-a-subject). | M3, M14 (without a subject) |
| **Process instance** | One run of a process. It is pinned to its release and records every step occurrence with its input, output, decision and error. | M3 |
| **Human task** | A step that waits for a person. It has an assignee, a form, a due date and allowed outcomes such as approve, return or reject. Exactly one final decision is recorded. The assignee is a user or a role, and a role holder can claim the task and release it. A task can be reassigned, a deadline can expire it and move the process on, and an escalation of a late task notifies people in-app and by email or reassigns it. See the [task API](../reference/task-api.md) and [task deadlines and claims](../reference/task-deadlines.md). | M3, M14 (deadlines and claims) |
| **Operator command** | An authorized, audited command on process work that the engine cannot finish alone. **Cancel** ends a `running` or `waiting` instance as `cancelled` and cancels its open tasks. **Retry** runs a `failed` instance again from its failed step, on its pinned release. **Resolve** settles a connector call or a package call whose outcome is `unknown`, as succeeded with output values or as failed. Each needs its own `process` grant and a reason, and writes a history row and an audit record. Cancel does not undo steps that already ran. See [operator commands](../reference/process-inspection.md#operator-commands). | M7 |
| **Retry policy** | A `callConnector` step and a package operation step declare their attempts and their backoff. The platform fixes which errors are retried, and the instance fails when attempts run out. An operator can then [retry](../reference/process-inspection.md#retry) it. See [call outcomes](../reference/process-execution.md#call-outcomes) and [package call outcomes](../reference/process-execution.md#package-call-outcomes). | M5 |
| **Dead letter** | A delivery that kept failing after `Worker:DeliveryAttempts` tries: an event to a trigger or a waiting instance, a schedule fan-out, an email or a webhook delivery. It is kept in `axis.dead_letters` until an operator redelivers or discards it, with a reason. See [dead letters](../reference/process-events.md#dead-letters). | M14, M18 (waking a waiting instance), M19 (webhook deliveries) |
| **Notification** | A message a `notify` operation or a task escalation sends to users, roles or email addresses, in the site (in-app) or by email. Its texts have named placeholders filled from typed values, never from a `sensitive` field. Email goes through an outbox and is sent at least once. See [notifications](../reference/notifications.md). | M14, M18 (escalation email) |
| **User profile** | What Axis keeps about a user who signed in: the user id, display name, email and locale, from the identity provider's claims. It gives notifications an address and a locale, a reassign its known users, a `userId` field its picker (both match by name or email) and history views the actor's name. It is not a user directory. See [user profiles](../reference/notifications.md#user-profiles). | M14 |
| **Process inspector** | A widget that names one process, lists its instances and opens one. It shows the graph with the path drawn on it, the tasks, and the connector and package calls with their attempts. A call's input is shown only when the user may read every field its mapping reads or writes, and a field marked `sensitive` is never shown. It needs an `inspect` grant on the process. The record history links to an instance. See [process inspection](../reference/process-inspection.md#process-inspection). | M7 |

**Step kinds** are operation, decision, human task, end, wait for event, timer and sub-process. See
[steps](../reference/processes.md#steps), and [process flow](../reference/process-flow.md) for the
waiting steps, loops through a waiting step, the `createRecord` operation and the email of the
`notify` operation.

## Triggers and integration

These concepts start work when something happens, and connect an application with other systems.

| Concept | Meaning | From |
| --- | --- | --- |
| **Trigger** | A `trigger` resource that starts a process when something happens: a data change, an event or a schedule, see the kinds below. Data change triggers fire on every write path: record API creates and updates, an inbound endpoint's create, task form saves, `updateRecord` and `createRecord` steps and connector and package operation outputs. The worker delivers raised events to `async` event triggers, and a `raiseEvent` step starts the processes of `sync` event triggers in its own transaction. See [events and triggers](../reference/integration-resources.md#events-and-triggers). | M5, M14 (delete triggers, scheduled jobs) |
| **Event** | An `event` resource: a named event about one entity, with typed payload fields. A `raiseEvent` step raises it for its subject record, and an inbound endpoint call with an `event` raises it for the record the call creates. Event triggers start processes from it, in the same transaction (sync) or through durable delivery (async). | M5, M19 (raised by an endpoint call) |
| **Connector** | A `connector` resource for calling an external system. It has a base URL from a `url` binding, auth from a `secret` binding, a timeout and named operations. It can name the idempotency header the system accepts, and each operation can name a lookup that finds an earlier call by its key. Its `auth` can be OAuth2 client credentials, where the worker gets an access token and sends it as a bearer token. Inputs can go in the path, query and headers, and an `object` or `list` input is sent as nested JSON. Outputs stay scalar and can name a `source`. See [connectors](../reference/integration-resources.md#connectors-and-deployment-bindings). | M5, M19 (OAuth2, structured payloads) |
| **Webhook** | A `webhook` resource that sends an event to another system's URL, signed with the Standard Webhooks headers. The author configures it in the application. Delivery is at least once, and a delivery that keeps failing becomes a dead letter. See [outbound webhooks](../reference/outbound-webhooks.md#outbound-webhooks). | M19 |
| **Endpoint** | An `endpoint` resource that lets another system, signed in with a bearer token, create a record, start a process on it, raise an event about it, or do more than one, in one call. It has typed input fields, the entity it creates, a mapping from input to fields, and an optional process and event. It can return output fields when the process completes within a short wait. Its calls take an idempotency key and answer with a status location. See [endpoints](../reference/integration-resources.md#endpoint-resource). | M5, M19 (raises an event) |

**Trigger kinds:**

- **Data change:** a record was created or updated, optionally only when named fields changed, or a
  record was deleted, which starts a process without a subject.
- **Event:** a named event was raised.
- **Schedule:** a cron schedule in an IANA time zone. Without a data source it starts a process
  without a subject once, a scheduled job. With one, it fans out over the records of a data source.

Inbound endpoints are their own resource, not a trigger kind, see
[D27](../decisions/d27-inbound-endpoints.md).

## Presentation

These concepts are what people see: sites, pages, widgets and their texts.

| Concept | Meaning | From |
| --- | --- | --- |
| **Site** | An entry point of one application, with its own path, title, locales (default, fallback and available) and navigation. A tenant host can be the site's own, which serves only that site, and `signIn` lists the identity providers the site allows. See [sites and sign-in](../reference/identity-provider.md#sites-and-sign-in). | M1, M17 (sign-in, own host) |
| **Page** | A route in a site. It has a title, and its content is its widgets: a tree of widgets, drawn in order. A page has no entity or template of its own. It can declare typed parameters, filled by navigate actions. | M1, M12 (widget tree, parameters) |
| **Widget** | A UI block on a page. The widgets are `table`, `form`, `taskInbox`, which lists the user's open tasks, the process inspector, the containers `columns`, `tabs` and `section`, which hold other widgets, and `detail`, `chart` and `kpi`. A `table` shows an entity or a data source, and opens and creates records through navigate actions. A chart and a KPI bind page parameters into their data source with the name map of a table. Custom widgets come from extension packages. See [frontend](../reference/frontend.md). | M1, M12 (containers, detail, chart and KPI widgets), M13 (chart and KPI page parameters), M22 (custom widgets) |
| **Custom widget** | A React component in an extension package that a page names as `<package>/<name>`, with typed properties. It builds on the widget SDK, never on Ant Design. It runs in the SPA with the user's session, so it is trusted code. The page designer's palette lists the widgets of the packages an application declares. See [custom widgets](../reference/custom-widgets.md). | M22 |
| **Form** | Fields laid out in sections and steps, with visible, required and read-only conditions, validation rules, child collections (line items), lookups and file upload. A `form` resource lays out an entity's fields in sections, any of them read-only, and both pages and tasks use it. Conditions are checked as the user types, and a wizard shows the steps one at a time. The task API refuses a value for a hidden or read-only field. See the [form resource and form widget](../reference/form-widget.md). | M1 (basic), M3 (form resource), M12 (states, steps), M13 (task API refusal), M15 (file upload) |
| **Action** | A user command on a page or widget: start a process, complete a task, navigate with page parameters, or a table row or toolbar action, delete included. Actions are always authorized on the server. A delete of a record that a running or waiting process instance works on is refused with `409`. Page metadata lists the actions, and the SPA shows their buttons on table rows, the table toolbar and saved forms. | M3, M12 (navigate, row and toolbar actions), M13 (delete refusal) |
| **Theme** | Design tokens for light and dark mode, shared by every site. No page adds styling of its own. | M1 |
| **Text resource** | A localized text with a stable key. Every UI string comes from text resources. An application has one `text` resource per locale, and every locale has the same keys. A key used by a label must exist in every locale. Texts are never shared across applications. Each release carries its own texts, so removing a key in a newer release does not affect work still running on an older one. | M1 (basic), M6 (full) |

## Security and operations

These concepts decide who may do what, where tenants live and how Axis is run and sold.

| Concept | Meaning | From |
| --- | --- | --- |
| **Role** | A declared `role` resource with a name and a label. A task assigned to a role, and each role a policy names, must name a declared role. Users hold roles through the identity provider's roles claim, and a claim value that names no declared role is ignored. An identity provider's `roles` mapping and the roles an administrator gives on the users page add to them, see [users](../reference/identity-provider.md#users). Policies give roles their grants. Every application endpoint matches the claim values. See [roles and policies](../reference/roles-and-policies.md) and [authorization](../reference/security.md#authorization). | M4, M17 (mapping, given roles) |
| **Policy** | A `policy` resource that gives one or more roles grants on entities, data sources and processes, and `invoke` on endpoints. An entity grant may have a record filter and a list of fields. The grants of all the user's policies combine with OR, and default-deny applies. The record API, the data source endpoint, the process start endpoint and the endpoint call enforce its grants, and the record API and the data source endpoint also enforce its record filters and field lists. Site navigation and page metadata follow a signed-in user's grants, and page metadata leaves out the fields the user may not read. See [roles and policies](../reference/roles-and-policies.md) and [authorization](../reference/security.md#authorization). | M4 |
| **Author** | An installation-level role, not a `role` resource. The setting `Studio:AuthorRole` names the roles claim value. A user who holds it may use Studio. With no value, nobody may. Application policies play no part. See [Studio settings](../reference/host-settings.md#studio-settings). | M8 |
| **Publisher role** | An installation-level role, not a `role` resource. The setting `Studio:PublisherRole` names the roles claim value. A user who holds it and the author role may publish from Studio and activate a release. With no value, nobody may. The host that runs the requests is the command `axis-admin publisher`, see [administration](../reference/administration.md#publisher). | M10 |
| **Operator console** | The `/console` page where the platform operator of a tenant sees failed work, dead letters, webhook deliveries, schedules and publishing across every application, and runs retry, cancel, resolve, redeliver and discard. The installation-level setting `Console:OperatorRole` names the roles claim value. Application policies play no part. See [operator console](../reference/operator-console.md). | M23 |
| **Identity provider** | An `identityProvider` resource: one way for an application's people to sign in, `accounts` that Axis's identity provider holds, or an `oidc` or `saml` provider that the tenant's realm brokers to, with its bindings, claims and role mapping. A site lists the ones it allows. See [Axis's identity provider](../reference/identity-provider.md). | M17, M28 (redirect addresses follow tenant hosts) |
| **Platform sign-in** | A tenant setting: the identity providers that the home page, Studio, the operator console and the users page accept, since they belong to no site. The platform roles come from it. See [platform sign-in](../reference/identity-provider.md#platform-sign-in). | M17 |
| **Administrator** | An installation-level role, not a `role` resource. The setting `Users:AdministratorRole` names the roles claim value. A user who holds it invites accounts and gives roles on the `/users` page, and disables, enables and resets an authenticator there. Application policies play no part. See [user administration](../reference/user-administration.md). | M17, M28 (disable, enable, reset authenticator) |
| **Tenant** | An isolated customer scope with its own database, users, applications and settings. | M1 (context), M9 (management) |
| **Tenant directory** | The list of tenants in the platform database: each tenant's status, hosts, database, sign-in settings and deployment bindings, with secrets stored encrypted. The server and the worker read it and pick up changes without a restart. Host configuration stays the default source. See [tenant directory](../architecture.md#tenant-directory). | M9 |
| **Tenant backup** | An archive of one tenant's database and its keys, written by `tenant backup` and read by `tenant restore`. It is encrypted with a backup key that the operator keeps outside the installation. See [tenant backup and restore](../reference/tenant-backup-and-restore.md). | M9, M27 (encrypted) |
| **Preview tenant** | A tenant that belongs to one main tenant, where an author tries an application before publishing it. It has its own database, hosts, deployment bindings and status, and its data never mixes with the main tenant's. Its bindings are empty by default, so it never calls a real system by accident. It signs people in with its main tenant's sign-in settings. Studio's **Preview** button sends a request that the publisher runs on it. See [preview tenants](../architecture.md#preview-tenants). | M10 |
| **Cell** | One full installation of Axis that Axis runs as a SaaS: the server, the worker, the publisher, PostgreSQL, the identity provider and file storage. Many tenants share a cell, or one customer has a cell of its own. Every tenant lives in exactly one cell. See [D118](../decisions/d118-axis-saas-in-cells-with-sign-up-quotas-and-billing.md) and [cells](../reference/cells.md). | M31 |
| **Region** | A place where customer data is kept, such as `vn` or `sg`. A region holds one or more cells, and a tenant's data, backups included, never leaves its region. See [regions and cells](../reference/cells.md#regions-and-cells). | M31 |
| **Quota** | A limit on what one tenant of a shared cell uses: storage, users, applications, emails a day and work at once. A write past a storage, user or application quota is refused, and work past a concurrency quota waits its turn. A refusal is a `403` with the reason `quota-exceeded`. See [tenant quotas](../reference/tenant-quotas.md). | M31 |
| **Usage** | What a tenant of a cell has used, measured and kept for 13 months: one row a day with its largest storage sample, its users and applications, the emails sent, the calls made and the work items run. It holds counts and sizes, never business data. The cell console shows it, a tenant's administrator sees its own on the users page, and plans read it. See [usage](../reference/tenant-quotas.md#usage). | M31 |
| **Cell console** | The page, on a host of its own, where the platform operator sees every tenant of a cell with its status, usage and failed work counts, and creates, suspends, exports and deletes tenants through the cell's provisioning API. The operator signs in through the operator realm, apart from every tenant realm, with a second factor. See [cell console](../reference/cell-console.md). | M31 |
| **Trial** | The first period of a tenant created by sign-up, 30 days with the quotas of a mid plan. Its administrators get emails before its end, it becomes read-only at the end and is deleted 30 days later, unless it becomes paid. See [subscriptions](../reference/subscriptions.md). | M33 |
