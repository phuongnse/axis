# Axis roadmap

## How work is planned

- **Milestones are vertical slices.** Each one ends with a running feature
  covered by automated tests, including at least one end-to-end journey.
- **Rolling wave.** A milestone is broken into issues only when it is meant to
  run and passes the readiness check, using what was learned. The issues of
  several milestones run at once, as
  [D68](decisions/d68-issues-of-several-milestones-run-at-once.md) describes.
  How is in [the life of a milestone](delivery.md#the-life-of-a-milestone).
- **Issue size.** One issue is one behaviour that fits in a single NexKit
  agent session. The sizing rule and how a `too_large` issue is split are in
  [the life of an issue](delivery.md#the-life-of-an-issue).
- **Docs first.** An issue links to the doc sections it implements. When an
  issue changes agreed behaviour, it updates the docs in the same pull request.
- **Cross-cutting qualities are built in, not added later.** Every milestone
  includes:
  - tenant isolation
  - authorization from M4
  - durable history from M3
  - basic performance sanity for the features it adds

## Milestones

Axis is designed for individuals and small and medium businesses first, and large organizations, banks
and government later, as [D166](decisions/d166-axis-is-designed-for-small-businesses-first-and-the-milestones-in-three-phases.md) agrees. The milestones after M18 are in three
phases, and each phase lists its milestones in the order they run. The
[direction](#direction) says why.

A milestone is **Planned** until it is broken into issues, **In progress** while it has open issues,
and **Done** once the owner closes it on GitHub. Breaking a milestone down sets In progress, and its
docs sweep sets Done.

| **M34** | Plans and billing | In progress | Each tenant has a plan, a named and versioned set of quotas with included users and no price, and a user pack adds users. Each call is idempotent, audited and rate limited, and the API has a version. Axis sends signed events to the billing system when a tenant is created, when a subscription changes state and with each tenant's daily usage, and a delivery retries with the same event id. A tenant paid through a date is active. Past that date it is past due, then read-only after the grace period, then deleting, and a new paid-through date brings it back. A downgrade is refused while the tenant's use is over the smaller plan. The journey: a billing system sets a trial tenant's plan and paid-through date and the tenant gets its new quotas, then lets the date pass, and the tenant ends read-only after the grace period. | **M35** | AI changes an application | In progress | Axis serves an MCP server over the authoring API, the only way any agent acts on Axis: its tools read resources, change drafts, write customization layers, validate and run scenarios, a client signs in through OAuth with its user's grants, and publishing is not a tool. The agent host is one of its clients. An author describes a change in words in Studio, the agent answers with a plan that the author approves, prefers declaring a built-in module and writing its layer to new resources, and writes scenarios for what it adds. The compiler, the scenarios and the contract scenarios run as its checks, a second agent session reviews the draft, and failures start a bounded fix round. Studio shows the draft's diff. The author accepts or drops it, or the agent accepts it when the application allows it. An accept is all or nothing, runs the checks again on the latest working folder, and waits in a queue of one accept at a time per application. Each accept and each Studio save is a revision that can be undone. The model is a binding of the kind `anthropic` or `openai-compatible` behind an adapter, and an authoring eval decides which models are supported. No record of the tenant reaches the model, each request is audited, and the threat model covers the MCP server. The journey: an author asks for a director's approval above a threshold on an approvals application, approves the plan, sees the layer change and its new scenario pass, and publishes; a request that would let a requester decide their own request is refused by the contract; a developer makes the same kind of change from an outside MCP client; and an accept whose resource another author changed meanwhile writes nothing and answers a conflict. It follows M25 and M26 and runs beside M31 to M34. See [D150](decisions/d150-each-authors-own-ai-with-axis-counting-no-requests.md). |

## Direction

[D46](decisions/d46-an-enterprise-application-platform-for-any-domain-and-the-milestones-after-m9.md) records the
direction after M9, and [D166](decisions/d166-axis-is-designed-for-small-businesses-first-and-the-milestones-in-three-phases.md) the people it is designed for first.

- **An enterprise application platform for any domain.** An author creates, configures, tests,
  publishes and runs an application through Studio, without editing JSON or
  code.
- **Small businesses first.** Individuals and small and medium businesses have no IT team and
  do not install software. They start from a built-in application, change it in Studio and use
  Axis SaaS that an operator runs, see [D168](decisions/d168-billing-is-the-operators-own-system-and-axis-keeps-plans-as-quotas-the-clock-and-a-billing-api.md). Large organizations,
  banks and government come in phase 3.
- **What sets Axis apart.** Built-in modules that a business changes anywhere,
  that keep their upgrades, and whose contract holds on every write, see
  [D102](decisions/d102-built-in-modules-open-to-change-and-bound-by-a-contract.md). An author
  can also describe a change in words, and an agent makes it under the same contract, wherever
  Axis runs, see [D150](decisions/d150-each-authors-own-ai-with-axis-counting-no-requests.md).
- **No domain gets platform code.** Samples prove the platform. Built-in
  modules serve real businesses as configuration, not platform code.
- **Vertical slices.** The milestones follow what an author does: create an application, then its
  data and UI, logic and workflow, permissions, try it out, validate and test, publish and operate.
  Each ends with an end-to-end journey, and the phases order the work, see
  [D166](decisions/d166-axis-is-designed-for-small-businesses-first-and-the-milestones-in-three-phases.md).
- **Order.** M25, M26 and M31 are done, so M33 and M35 run next. M34 follows M33, see
  [D168](decisions/d168-billing-is-the-operators-own-system-and-axis-keeps-plans-as-quotas-the-clock-and-a-billing-api.md). M35 runs beside M33
  and M34, see [D150](decisions/d150-each-authors-own-ai-with-axis-counting-no-requests.md). In phase 2, M29 follows M25, M38 to M43 come
  before M30, which follows M26 and needs them, and M36 follows M35, see [D154](decisions/d154-every-capability-an-organization-needs-has-a-home-and-a-capability-map-keeps-it-so.md). M21 is done, and M37 runs once M34 and M35 are done.
- **Proving it is general.** From M11 on, each milestone extends a sample of a
  new shape: a service desk, then asset management. Neither needs platform
  code.
  M19 to M23 extend the purchase request sample instead, as
  [D94](decisions/d94-purchase-requests-prove-the-extensibility-milestone.md)
  agrees. From M26 the samples become built-in modules that real businesses
  customize, and phase 1 proves its work on them wherever it can.
- **Planning.** A milestone is broken into issues when it passes the readiness
  check of [D68](decisions/d68-issues-of-several-milestones-run-at-once.md).
  Only the milestones of the current phase are broken down, unless the owner
  asks for another, see [D166](decisions/d166-axis-is-designed-for-small-businesses-first-and-the-milestones-in-three-phases.md).
  The decisions and doc sections a milestone lacks are written first, as NexKit docs
  issues, as [the life of a milestone](delivery.md#the-life-of-a-milestone) describes.
