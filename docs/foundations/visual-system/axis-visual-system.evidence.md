## Current verification

- `frontend/ui-coverage-profile.json` defines `axis-ui-v1`: an auditable visual, behavioral, external-standard, and lifecycle requirement set with required evidence kinds, representative modes, and invalidation triggers. The requirement count is version-specific rather than a universal sufficiency claim. `frontend/ui-foundation.json` must classify every requirement exactly once as covered, gap, or explicitly allowed not-applicable. `check ui-foundation` resolves covered entries to real Acceptance Test Matrix ids and matching evidence-sidecar rows, requires the referenced evidence to be declared by the contract and satisfy the profile's evidence kinds and modes, distinguishes missing/candidate/accepted perceptual artifacts, rejects advanced state with gaps or pending acceptance, and rejects drift between state and `enforcedContracts`. The checker enforces traceability, not WCAG/ISO conformance or perceptual adequacy; those still require criterion-level assessment and review.
- The finite consumer mapping lives in typed source, its enforced-contract key set is derived from the manifest registry, and the real-symbol registry is compiler-checked for missing or extra owners and implementations. Contract owners require a compatible surface id, while focused component/browser evidence asserts emitted id/contract markers. No filename or source-text import pattern is treated as architectural proof. Reusable visual values are separately validated and projected from the canonical theme into the typed `axisStyles` contract; the theme gate rejects canonical text pairs below 4.5:1 and focus or input control boundaries below 3:1 against supported canvases. An AST-based consumption gate prevents authored code from bypassing that contract. Project-owner authority and review authenticity remain task or pull-request evidence, not manifest claims.
- The canonical input boundary now measures at least 3:1 against base, card, and popover canvases in both themes, and the theme gate rejects regression. Resting text-entry and outline-control fills inherit their owning canvas rather than reusing that stronger boundary token; selected, disabled, hover, and focus states remain independently visible. Account, Authenticated Frame, Entry Surface, Resource Workspace, and Managed Task Window each have an accepted five-capture matrix covering light/dark desktop/compact plus VI at the 320 CSS-pixel reflow boundary. All five have complete 18/18 requirement coverage and are enforced after project-owner review.
- Account retains its complete owner anatomy, top-aligned identity icon, Workspace continuity/recovery, preferences, sign-out, keyboard behavior, pending geometry, target density, localization, and scroll ownership. Authenticated Frame retains its complete owner/consumer inventory, empty Dashboard main, viewport ownership, navigation, context transition, and recovery evidence. Entry Surface retains one owner, six real consumers, clean-cutover proof, responsive density, and first-line consent-alignment guards. Resource Workspace retains six consumers, internal table scrolling, collection states, and 32/44 CSS-pixel control density. Managed Task Window retains six consumer families and additionally proves numeric visible-text and non-text contrast, native boundary-only focus wrapping that excludes non-rendered controls, guarded busy close, stable header selection behavior, and accepted captures.
- Solution Delivery now consumes the unchanged enforced Resource Workspace and Managed Task Window owners with typed registration and focused product-state/browser evidence. The unused Process Workbench owner, mapping, wrapper, and representative test are retired cleanly; no compatibility path or parallel composition remains. Existing journeys or artifacts do not advance lifecycle by themselves; requirement-complete evidence and explicit project-owner acceptance remain required for any new or revised owner contract.
