# ASVS: data and operations

The requirements of ASVS chapters V11 to V17, on cryptography, communication, configuration, data, secure coding, logging and WebRTC. How the rows are filled and checked is in [ASVS](asvs.md#how-it-is-filled).

## V11 Cryptography

The requirements of ASVS chapter V11, on cryptography.

| Id | Requirement | Status | Evidence |
| --- | --- | --- | --- |
| `V11.1.1` | Verify that there is a documented policy for management of cryptographic keys and a cryptographic key lifecycle that follows a key management standard such as NIST SP 800-57. This should include ensuring that keys are not overshared (for example, with more than two entities for shared secrets and more than one entity for private keys). | **Met** | The [key policy](keys-and-data-protection.md#key-policy) states the lifecycle of each key in NIST SP 800-57 terms, including rotation with [`platform rekey`](tenant-setting-commands.md#installation-key). `PlatformRekeyTests` covers the rekey. |
| `V11.1.2` | Verify that a cryptographic inventory is performed, maintained, regularly updated, and includes all cryptographic keys, algorithms, and certificates used by the application. It must also document where keys can and cannot be used in the system, and the types of data that can and cannot be protected using the keys. | **Met** | The [cryptographic inventory](keys-and-data-protection.md#cryptographic-inventory) lists every key, algorithm and certificate, with where each may and may not be used and its lifecycle. |
| `V11.2.1` | Verify that industry-validated implementations (including libraries and hardware-accelerated implementations) are used for cryptographic operations. | **Met** | `TenantSecretCipherTests`: the installation key encrypts with the .NET AES-GCM implementation, see [platform database](storage.md#platform-database). |
| `V11.2.2` | Verify that the application is designed with crypto agility such that random number, authenticated encryption, MAC, or hashing algorithms, key lengths, rounds, ciphers and modes can be reconfigured, upgraded, or swapped at any time, to protect against cryptographic breaks. Similarly, it must also be possible to replace keys and passwords and re-encrypt data. This will allow for seamless upgrades to post-quantum cryptography (PQC), once high-assurance implementations of approved PQC schemes or standards are widely available. | **Met** | [Crypto agility](keys-and-data-protection.md#crypto-agility) describes the replacement path. Every stored secret goes through `TenantSecretCipher`, and `platform rekey` re-encrypts every value. The stored format has no algorithm id. `PlatformRekeyTests` and `TenantSecretCipherTests` cover the path. |
| `V11.2.3` | Verify that all cryptographic primitives utilize a minimum of 128-bits of security based on the algorithm, key size, and configuration. For example, a 256-bit ECC key provides roughly 128 bits of security where RSA requires a 3072-bit key to achieve 128 bits of security. | **Met** | Axis's own keys are AES-256, SHA-256, ES256 and 256-bit random ids. `DpopProofTests`: a `PS256` proof needs an RSA key of at least 2048 bits, the floor of FAPI 2.0. That key gives about 112 bits of security, less than the 3072 bits that this row names for 128, so the row rests on the FAPI 2.0 floor. |
| `V11.3.1` | Verify that insecure block modes (e.g., ECB) and weak padding schemes (e.g., PKCS#1 v1.5) are not used. | **Met** | `TenantSecretCipherTests`: the only block mode is AES-GCM, see [platform database](storage.md#platform-database). |
| `V11.3.2` | Verify that only approved ciphers and modes such as AES with GCM are used. | **Met** | `TenantSecretCipherTests`: AES-256-GCM, see [platform database](storage.md#platform-database). |
| `V11.3.3` | Verify that encrypted data is protected against unauthorized modification preferably by using an approved authenticated encryption method or by combining an approved encryption method with an approved MAC algorithm. | **Met** | `TenantSecretCipherTests`: a changed byte, another key, another tenant or another field does not decrypt, see [platform database](storage.md#platform-database). |
| `V11.4.1` | Verify that only approved hash functions are used for general cryptographic use cases, including digital signatures, HMAC, KDF, and random bit generation. Disallowed hash functions, such as MD5, must not be used for any cryptographic purpose. | **Met** | Axis uses SHA-256 for the session id's hash, see [sign-in and the session](security.md#sign-in-and-the-session), and for a resource's version, see [versions](authoring.md#versions). SHA-1 has two uses. It names a resource as a version 5 UUID and secures nothing. The TOTP policy that `tenant create` writes to each tenant realm uses HMAC-SHA1, the default of [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238) that authenticator apps support. SHA-1's collision weakness does not affect an HMAC. See the [cryptographic inventory](keys-and-data-protection.md#cryptographic-inventory). |
| `V11.4.2` | Verify that passwords are stored using an approved, computationally intensive, key derivation function (also known as a "password hashing function"), with parameter settings configured based on current guidance. The settings should balance security and performance to make brute-force attacks sufficiently challenging for the required level of security. | **Not applicable** | Axis has no passwords of its own, see [D9](../decisions/d9-authentication-oidc-through-a-bff-ready-for-fapi-20.md). The database passwords it must present are stored encrypted, not hashed. |
| `V11.4.3` | Verify that hash functions used in digital signatures, as part of data authentication or data integrity are collision resistant and have appropriate bit-lengths. If collision resistance is required, the output length must be at least 256 bits. If only resistance to second pre-image attacks is required, the output length must be at least 128 bits. | **Met** | A resource's version is the SHA-256 of its whole file, see [versions](authoring.md#versions). The 16-character hash only shortens database identifiers and secures nothing. |
| `V11.4.4` | Verify that the application uses approved key derivation functions with key stretching parameters when deriving secret keys from passwords. The parameters in use must balance security and performance to prevent brute-force attacks from compromising the resulting cryptographic key. | **Not applicable** | Axis derives no key from a password. The installation key is 32 random bytes that the operator sets. |
| `V11.5.1` | Verify that all random numbers and strings which are intended to be non-guessable must be generated using a cryptographically secure pseudo-random number generator (CSPRNG) and have at least 128 bits of entropy. Note that UUIDs do not respect this condition. | **Met** | The session id is 256 bits from the system's random number generator, see [sign-in and the session](security.md#sign-in-and-the-session). The database passwords are 32 random bytes from the same generator. |
| `V11.6.1` | Verify that only approved cryptographic algorithms and modes of operation are used for key generation and seeding, and digital signature generation and verification. Key generation algorithms must not generate insecure keys vulnerable to known attacks, for example, RSA keys which are vulnerable to Fermat factorization. | **Met** | `ClientAssertionTests` and `DpopTokenRequestTests`: keys are EC P-256 and signatures are ES256, see [FAPI 2.0 profile](fapi2-profile.md). |

The proxy ends TLS, see [D49](../decisions/d49-several-server-replicas-behind-a-tls-proxy.md). |
| `V12.1.3` | Verify that the application validates that mTLS client certificates are trusted before using the certificate identity for authentication or authorization. | **Met** | Only a cell's internal listener asks for a client certificate, and it accepts one only when it chains to the region's internal certificate authority, see [provisioning API](tenant-lifecycle.md#provisioning-api). | `V12.2.1` | Verify that TLS is used for all connectivity between a client and external facing, HTTP-based services, and does not fall back to insecure or unencrypted communications. | **Met** | [TLS](installation.md#tls) states that clients reach Axis over TLS only, with no plain HTTP. The hosts publish only on `127.0.0.1` and the proxy publishes only container port 443. The Helm chart renders no Ingress and a `ClusterIP` server Service. `scripts/onprem.test.mjs` (the static Caddyfile check and smoke step 8) and `scripts/helm.test.mjs`. | `V12.2.2` | Verify that external facing services use publicly trusted TLS certificates. | **Met** | [TLS](installation.md#tls) tells the operator to use a publicly trusted certificate that covers every tenant host. The certificate comes with the operator's proxy, and no test checks it. The proxy ends TLS, see [D49](../decisions/d49-several-server-replicas-behind-a-tls-proxy.md). |
| `V12.3.1` | Verify that an encrypted protocol such as TLS is used for all inbound and outbound connections to and from the application, including monitoring systems, management tools, remote access and SSH, middleware, databases, mainframes, partner systems, or external APIs. The server must not fall back to insecure or unencrypted protocols. | **Met** | The proxy ends TLS, see [D49](../decisions/d49-several-server-replicas-behind-a-tls-proxy.md). [TLS](installation.md#tls) states the rule. [URL bindings](integration-resources.md#deployment-bindings) must be `https` outside Development. Outside Development and Testing the server, the worker, the publisher and the admin tool stop at start when their own connection strings set `SSL Mode` below `VerifyFull`, see `DatabaseTlsRequirementTests`, `DatabaseTlsStartTests`, `AdminDatabaseTlsTests` and `WorkerOptionsTests`. The on-premises smoke test checks in `pg_stat_ssl` that every Axis connection uses TLS. Outside Development the worker sends no email with `Email:Smtp:UseTls` off and `tenant email set` refuses `--tls false`, and the server and the worker stop at start on an OTLP endpoint that is not `https`, see `NotificationEmailTests`, `AdminTenantEmailSetTests`, `WorkerOptionsTests` and `ServerTelemetryTests`. The servers serve HTTPS only, see V12.3.3. |
| `V12.3.2` | Verify that TLS clients validate certificates received before communicating with a TLS server. | **Met** | `TenantDatabaseTlsTests` and `DirectoryTenantTlsTests`: tenant connections copy the TLS settings of the host's own connection string, and under `SSL Mode=Require` a connection to a server without TLS fails. `DatabaseTlsRequirementTests`: outside Development and Testing, only `SSL Mode=VerifyFull` passes for a host's own connection string. See [TLS](installation.md#tls) for PostgreSQL under `VerifyFull` and for the identity provider. The proxy ends TLS, see [D49](../decisions/d49-several-server-replicas-behind-a-tls-proxy.md). |
| `V12.3.3` | Verify that TLS or another appropriate transport encryption mechanism used for all connectivity between internal, HTTP-based services within the application, and does not fall back to insecure or unencrypted communications. | **Met** | The servers listen on HTTPS only and have no plain HTTP listener, so the proxy cannot fall back to unencrypted traffic. The Compose proxy connects over TLS and the Helm chart serves HTTPS and probes it over HTTPS, see [D49](../decisions/d49-several-server-replicas-behind-a-tls-proxy.md) and [TLS](installation.md#tls). `scripts/onprem.test.mjs` checks the Kestrel HTTPS settings, the Caddyfile and the certificate mounts statically, and in smoke step 8 checks that the proxy serves the sample and sign-in through servers that answer plain HTTP with nothing. `scripts/helm.test.mjs` checks the HTTPS port, the probes and the Service. The worker's health endpoint stays plain HTTP and carries no application traffic, see [TLS](installation.md#tls). |
| `V12.3.4` | Verify that TLS connections between internal services use trusted certificates. Where internally generated or self-signed certificates are used, the consuming service must be configured to only trust specific internal CAs and specific self-signed certificates. | **Met** | The Compose proxy checks the server name `servers` and trusts only the authority certificate `server-ca.crt`, never the system roots and never a skipped verification, see [TLS](installation.md#tls) and [D49](../decisions/d49-several-server-replicas-behind-a-tls-proxy.md). `scripts/onprem.test.mjs` checks the Caddyfile's trust pool statically, and smoke step 8 runs the proxy against servers with a certificate of that authority. With Helm, the server certificate is a Kubernetes TLS Secret that you name, and your Ingress must verify it, see `scripts/helm.test.mjs` for the Secret and the HTTPS port. |
