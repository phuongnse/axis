# ASVS: identity and access

The requirements of ASVS chapters V6 to V10, on authentication, sessions, authorization, tokens and OAuth. How the rows are filled and checked is in [ASVS](asvs.md#how-it-is-filled).

| `V6.5.2` | Verify that, when being stored in the application's backend, lookup secrets with less than 112 bits of entropy (19 random alphanumeric characters or 34 random digits) are hashed with an approved password storage hashing algorithm that incorporates a 32-bit random salt. | `V6.5.3` | Verify that lookup secrets, out-of-band authentication code, and time-based one-time password seeds, are generated using a Cryptographically Secure Pseudorandom Number Generator (CSPRNG) to avoid predictable values. | **Delegated** | The identity provider's, [D9](../decisions/d9-authentication-oidc-through-a-bff-ready-for-fapi-20.md), see [sign-in and the session](security.md#sign-in-and-the-session). |
| `V6.5.4` | Verify that lookup secrets and out-of-band authentication codes have a minimum of 20 bits of entropy (typically 4 random alphanumeric characters or 6 random digits is sufficient). | **Delegated** | The identity provider's, [D9](../decisions/d9-authentication-oidc-through-a-bff-ready-for-fapi-20.md), see [sign-in and the session](security.md#sign-in-and-the-session). |

| `V6.6.1` | Verify that authentication mechanisms using the Public Switched Telephone Network (PSTN) to deliver One-time Passwords (OTPs) via phone or SMS are offered only when the phone number has previously been validated, alternate stronger methods (such as Time based One-time Passwords) are also offered, and the service provides information on their security risks to users. For L3 applications, phone and SMS must not be available as options. | **Delegated** | The identity provider's, [D9](../decisions/d9-authentication-oidc-through-a-bff-ready-for-fapi-20.md), see [sign-in and the session](security.md#sign-in-and-the-session). |
| `V6.6.2` | Verify that out-of-band authentication requests, codes, or tokens are bound to the original authentication request for which they were generated and are not usable for a previous or subsequent one. | **Delegated** | The identity provider's, [D9](../decisions/d9-authentication-oidc-through-a-bff-ready-for-fapi-20.md), see [sign-in and the session](security.md#sign-in-and-the-session). |
| `V6.6.3` | Verify that a code based out-of-band authentication mechanism is protected against brute force attacks by using rate limiting. | `V6.8.1` | Verify that, if the application supports multiple identity providers (IdPs), the user's identity cannot be spoofed via another supported identity provider (eg. by using the same user identifier). The standard mitigation would be for the application to register and identify the user using a combination of the IdP ID (serving as a namespace) and the user's ID in the IdP. | **Met** | Axis trusts one issuer for each tenant, the tenant's realm, so the user id is the realm's `sub`. The realm names each brokered user after its provider and never links two providers by email, `RealmBrokeredUsersTests`, see [users](identity-provider.md#users). The callback reads the `identity_provider` claim and refuses a provider that the site or the platform sign-in does not allow, `SiteSignInTests`, see [sites and sign-in](identity-provider.md#sites-and-sign-in). `SignInTests`: a callback from another tenant's sign-in is refused. |
| `V6.8.2` | Verify that the presence and integrity of digital signatures on authentication assertions (for example on JWTs or SAML assertions) are always validated, rejecting any assertions that are unsigned or have invalid signatures. | **Met** | `EndpointCallerTests` and `SignInTests`: an unusable token is a `401`, and the OIDC handler checks the ID token's signature. |
| `V6.8.3` | Verify that SAML assertions are uniquely processed and used only once within the validity period to prevent replay attacks. | **Delegated** | The tenant's realm at the identity provider receives and checks every SAML assertion, and Axis receives none. Axis gets only the realm's OIDC ID token, see [D9](../decisions/d9-authentication-oidc-through-a-bff-ready-for-fapi-20.md). The realm sync imports each `saml` provider from its metadata, signs the realm's requests with RSA-SHA256 and asks for a persistent NameID, see [keeping the realm in step](identity-provider.md#keeping-the-realm-in-step). |
| `V6.8.4` | Verify that, if an application uses a separate Identity Provider (IdP) and expects specific authentication strength, methods, or recentness for specific functions, the application verifies this using the information returned by the IdP. For example, if OIDC is used, this might be achieved by validating ID Token claims such as 'acr', 'amr', and 'auth_time' (if present). If the IdP does not provide this information, the application must have a documented fallback approach that assumes that the minimum strength authentication mechanism was used (for example, single-factor authentication using username and password). | **Met** | `SignInRecencyTests`: the callback checks the ID token's `auth_time` and refuses a token without it or with one older than the session's lifetime. A site sign-in through a provider with an `acr` list also asks for those levels and is refused as `acrNotAccepted` when the upstream `acr` is missing or not in the list, see `SiteSignInTests`. Axis expects no other strength or method, and asks for no `amr`. |

## V9 Self-contained Tokens

The requirements of ASVS chapter V9, on self-contained tokens.

| Id | Requirement | Status | Evidence |
| --- | --- | --- | --- |
| `V9.1.1` | Verify that self-contained tokens are validated using their digital signature or MAC to protect against tampering before accepting the token's contents. | **Met** | `EndpointCallerTests`: a wrongly signed token is a `401`. The signature is checked with the issuer's published keys, see [machine callers](security.md#machine-callers). |
| `V9.1.2` | Verify that only algorithms on an allowlist can be used to create and verify self-contained tokens, for a given context. The allowlist must include the permitted algorithms, ideally only either symmetric or asymmetric algorithms, and must not include the 'None' algorithm. If both symmetric and asymmetric must be supported, additional controls will be needed to prevent key confusion. | **Met** | `ServiceAccountBearerOptionsTests` shows that both bearer schemes allow only `RS`, `PS` and `ES` algorithms, and `EndpointCallerTests`: a token signed with `HS256` or `none` is a `401`. `DpopProofTests`: a proof may use only `ES256` or `PS256`. See [machine callers](security.md#machine-callers) and [FAPI 2.0 profile](fapi2-profile.md). |
| `V9.1.3` | Verify that key material that is used to validate self-contained tokens is from trusted pre-configured sources for the token issuer, preventing attackers from specifying untrusted sources and keys. For JWTs and other JWS structures, headers such as 'jku', 'x5u', and 'jwk' must be validated against an allowlist of trusted sources. | **Met** | `EndpointCallerTests`: the keys come from the `Authority` of the tenant, which an operator sets, and a token of another tenant's issuer is a `401`, see [machine callers](security.md#machine-callers). |
| `V9.2.1` | Verify that, if a validity time span is present in the token data, the token and its content are accepted only if the verification time is within this validity time span. For example, for JWTs, the claims 'nbf' and 'exp' must be verified. | **Met** | `EndpointCallerTests`: an expired token is a `401`. The expiry and the start time are checked against the server's clock, see [machine callers](security.md#machine-callers). |
| `V9.2.2` | Verify that the service receiving a token validates the token to be the correct type and is meant for the intended purpose before accepting the token's contents. For example, only access tokens can be accepted for authorization decisions and only ID Tokens can be used for proving user authentication. | **Met** | `EndpointCallerTests`: an ID token whose audience the tenant expects is a `401`, because only a token that is not marked as another type is an access token. See [machine callers](security.md#machine-callers). |
| `V9.2.3` | Verify that the service only accepts tokens which are intended for use with that service (audience). For JWTs, this can be achieved by validating the 'aud' claim against an allowlist defined in the service. | **Met** | `EndpointCallerTests` and `ServiceAccountBearerOptionsTests`: a token without the tenant's endpoint or service audience is a `401`, see [service accounts](security.md#service-accounts). |
| `V9.2.4` | Verify that, if a token issuer uses the same private key for issuing tokens to different audiences, the issued tokens contain an audience restriction that uniquely identifies the intended audiences. This will prevent a token from being reused with an unintended audience. If the audience identifier is dynamically provisioned, the token issuer must validate these audiences in order to make sure that they do not result in audience impersonation. | **Delegated** | The identity provider issues every token and sets its audience. Axis issues none, see [D9](../decisions/d9-authentication-oidc-through-a-bff-ready-for-fapi-20.md). |

## V10 OAuth and OIDC

The requirements of ASVS chapter V10, on OAuth 2.0 and OpenID Connect.

| Id | Requirement | Status | Evidence |
| --- | --- | --- | --- |
| `V10.1.1` | Verify that tokens are only sent to components that strictly need them. For example, when using a backend-for-frontend pattern for browser-based JavaScript applications, access and refresh tokens shall only be accessible for the backend. | **Met** | `SessionTokensTests`: the only token the server keeps is the platform client's refresh token, encrypted in the session row, and no response carries one. `SignInTests` shows that a tenant without a data key keeps none, see [sign-in and the session](security.md#sign-in-and-the-session). |
| `V10.1.2` | Verify that the client only accepts values from the authorization server (such as the authorization code or ID Token) if these values result from an authorization flow that was initiated by the same user agent session and transaction. This requires that client-generated secrets, such as the proof key for code exchange (PKCE) 'code_verifier', 'state' or OIDC 'nonce', are not guessable, are specific to the transaction, and are securely bound to both the client and the user agent session in which the transaction was started. | **Met** | `SignInTests`: a callback with no readable state, or with the state of another tenant's sign-in, is refused. `SignInRefusalsTests` covers the refusal reasons, see [sign-in and the session](security.md#sign-in-and-the-session). |
| `V10.2.1` | Verify that, if the code flow is used, the OAuth client has protection against browser-based request forgery attacks, commonly known as cross-site request forgery (CSRF), which trigger token requests, either by using proof key for code exchange (PKCE) functionality or checking the 'state' parameter that was sent in the authorization request. | **Met** | `SignInTests`: sign-in uses PKCE and a state that the correlation cookie holds, see [sign-in and the session](security.md#sign-in-and-the-session). |
| `V10.2.2` | Verify that, if the OAuth client can interact with more than one authorization server, it has a defense against mix-up attacks. For example, it could require that the authorization server return the 'iss' parameter value and validate it in the authorization response and the token response. | **Met** | Each tenant's client talks to one identity provider, and a callback of another tenant's sign-in is refused (`SignInTests`). A `fapi2` tenant also checks the `iss` parameter (`Fapi2SignInTests`), see [FAPI 2.0 profile](fapi2-profile.md). |
| `V10.3.1` | Verify that the resource server only accepts access tokens that are intended for use with that service (audience). The audience may be included in a structured access token (such as the 'aud' claim in JWT), or it can be checked using the token introspection endpoint. | **Met** | `EndpointCallerTests` and `ServiceAccountBearerOptionsTests`: a token without the expected audience is a `401`, see [machine callers](security.md#machine-callers). |
| `V10.3.2` | Verify that the resource server enforces authorization decisions based on claims from the access token that define delegated authorization. If claims such as 'sub', 'scope', and 'authorization_details' are present, they must be part of the decision. | **Met** | A decision uses the caller id and the roles claim. Policies grant by role and the identity provider gives the service account its roles, so the roles claim carries its delegated authority. `ServiceAccountRecordTests` shows the decision, and the reason is in the [scope](security.md#service-accounts) bullet of service accounts. |
| `V10.3.3` | Verify that if an access control decision requires identifying a unique user from an access token (JWT or related token introspection response), the resource server identifies the user from claims that cannot be reassigned to other users. Typically, it means using a combination of 'iss' and 'sub' claims. | **Met** | The caller id is the `sub` claim by default, and the audit actor. `EndpointCallerTests` shows it, see [machine callers](security.md#machine-callers). |
| `V10.3.4` | Verify that, if the resource server requires specific authentication strength, methods, or recentness, it verifies that the presented access token satisfies these constraints. For example, if present, using the OIDC 'acr', 'amr' and 'auth_time' claims respectively. | **Not applicable** | Axis requires no authentication strength, method or recentness of an inbound endpoint token, so it checks none of the `acr`, `amr` or `auth_time` claims there. Only browser sign-in checks `auth_time`, see [session lifetimes and re-authentication](security.md#session-lifetimes-and-re-authentication). |
| `V10.4.1` | Verify that the authorization server validates redirect URIs based on a client-specific allowlist of pre-registered URIs using exact string comparison. | **Delegated** | The identity provider meets it, see [D9](../decisions/d9-authentication-oidc-through-a-bff-ready-for-fapi-20.md). |
| `V10.4.2` | Verify that, if the authorization server returns the authorization code in the authorization response, it can be used only once for a token request. For the second valid request with an authorization code that has already been used to issue an access token, the authorization server must reject a token request and revoke any issued tokens related to the authorization code. | **Delegated** | The identity provider meets it, see [D9](../decisions/d9-authentication-oidc-through-a-bff-ready-for-fapi-20.md). |
| `V10.4.3` | Verify that the authorization code is short-lived. The maximum lifetime can be up to 10 minutes for L1 and L2 applications and up to 1 minute for L3 applications. | **Delegated** | The identity provider meets it, see [D9](../decisions/d9-authentication-oidc-through-a-bff-ready-for-fapi-20.md). |
| `V10.4.4` | Verify that for a given client, the authorization server only allows the usage of grants that this client needs to use. Note that the grants 'token' (Implicit flow) and 'password' (Resource Owner Password Credentials flow) must no longer be used. | **Delegated** | The identity provider meets it, see [D9](../decisions/d9-authentication-oidc-through-a-bff-ready-for-fapi-20.md). Axis uses only the code flow and, for machine callers, the client credentials grant. |
| `V10.4.5` | Verify that the authorization server mitigates refresh token replay attacks for public clients, preferably using sender-constrained refresh tokens, i.e., Demonstrating Proof of Possession (DPoP) or Certificate-Bound Access Tokens using mutual TLS (mTLS). For L1 and L2 applications, refresh token rotation may be used. If refresh token rotation is used, the authorization server must invalidate the refresh token after usage, and revoke all refresh tokens for that authorization if an already used and invalidated refresh token is provided. | **Delegated** | The identity provider meets it, see [D9](../decisions/d9-authentication-oidc-through-a-bff-ready-for-fapi-20.md). Axis registers no public client, and the one refresh token it keeps is its own confidential client's, see [the refresh token](security.md#sign-in-flow). A public client that an operator adds to a tenant realm gets refresh tokens that work once, see [sign-in](mcp-server.md#sign-in). |
| `V10.4.6` | Verify that, if the code grant is used, the authorization server mitigates authorization code interception attacks by requiring proof key for code exchange (PKCE). For authorization requests, the authorization server must require a valid 'code_challenge' value and must not accept a 'code_challenge_method' value of 'plain'. For a token request, it must require validation of the 'code_verifier' parameter. | **Delegated** | The identity provider meets it, see [D9](../decisions/d9-authentication-oidc-through-a-bff-ready-for-fapi-20.md). Axis sends a PKCE challenge, see `SignInTests`. A tenant realm refuses a public client's request without an `S256` challenge, see [sign-in](mcp-server.md#sign-in). |
| `V10.4.7` | Verify that if the authorization server supports unauthenticated dynamic client registration, it mitigates the risk of malicious client applications. It must validate client metadata such as any registered URIs, ensure the user's consent, and warn the user before processing an authorization request with an untrusted client application. | **Met** | The realm validates the registered redirect addresses, the flows, the client type and the scope, and requires consent, which `TenantRealmAuthoringTests` shows. See [client registration](mcp-server.md#client-registration). |
| `V10.4.8` | Verify that refresh tokens have an absolute expiration, including if sliding refresh token expiration is applied. | **Delegated** | The identity provider meets it, see [D9](../decisions/d9-authentication-oidc-through-a-bff-ready-for-fapi-20.md). |
| `V10.4.9` | Verify that refresh tokens and reference access tokens can be revoked by an authorized user using the authorization server user interface, to mitigate the risk of malicious clients or stolen tokens. | **Delegated** | The identity provider meets it, see [D9](../decisions/d9-authentication-oidc-through-a-bff-ready-for-fapi-20.md). |
| `V10.4.10` | Verify that confidential client is authenticated for client-to-authorized server backchannel requests such as token requests, pushed authorization requests (PAR), and token revocation requests. | **Met** | `SignInTests` and `Fapi2SignInTests`: the token request carries the client secret, or a `private_key_jwt` assertion under `fapi2`, which also covers pushed authorization requests, see [FAPI 2.0 profile](fapi2-profile.md). |
| `V10.4.11` | Verify that the authorization server configuration only assigns the required scopes to the OAuth client. | **Delegated** | The identity provider meets it, see [D9](../decisions/d9-authentication-oidc-through-a-bff-ready-for-fapi-20.md). Axis asks only for the `openid`, `profile` and `email` scopes. |
| `V10.5.1` | Verify that the client (as the relying party) mitigates ID Token replay attacks. For example, by ensuring that the 'nonce' claim in the ID Token matches the 'nonce' value sent in the authentication request to the OpenID Provider (in OAuth2 refereed to as the authorization request sent to the authorization server). | **Met** | `SignInTests`: a callback whose ID token carries a nonce that the sign-in did not send creates no session and is refused as `invalidToken`, see [security](security.md#authentication-and-authorization). |
| `V10.5.2` | Verify that the client uniquely identifies the user from ID Token claims, usually the 'sub' claim, which cannot be reassigned to other users (for the scope of an identity provider). | **Met** | `SignInTests`: the user comes from the configured user id claim, `sub` by default, see [sign-in and the session](security.md#sign-in-and-the-session). |
| `V10.5.3` | Verify that the client rejects attempts by a malicious authorization server to impersonate another authorization server through authorization server metadata. The client must reject authorization server metadata if the issuer URL in the authorization server metadata does not exactly match the pre-configured issuer URL expected by the client. | **Met** | `SignInTests`: provider metadata whose `issuer` is not the tenant's `Authority` creates no session and is refused as `invalidIssuer`, before the code goes to the token endpoint, see [security](security.md#authentication-and-authorization). |
| `V10.5.4` | Verify that the client validates that the ID Token is intended to be used for that client (audience) by checking that the 'aud' claim from the token is equal to the 'client_id' value for the client. | **Met** | `SignInTests`: an ID token whose `aud` is not the client id creates no session and is refused as `invalidToken`, and the same re-signed token with the right `aud` signs in. |
| `V10.5.5` | Verify that, when using OIDC back-channel logout, the relying party mitigates denial of service through forced logout and cross-JWT confusion in the logout flow. The client must verify that the logout token is correctly typed with a value of 'logout+jwt', contains the 'event' claim with the correct member name, and does not contain a 'nonce' claim. Note that it is also recommended to have a short expiration (e.g., 2 minutes). | **Not applicable** | Axis serves no back-channel logout endpoint. Sign-out goes through `POST /api/auth/sign-out`, see [sign-in and the session](security.md#sign-in-and-the-session). |
| `V10.6.1` | Verify that the OpenID Provider only allows values 'code', 'ciba', 'id_token', or 'id_token code' for response mode. Note that 'code' is preferred over 'id_token code' (the OIDC Hybrid flow), and 'token' (any Implicit flow) must not be used. | **Delegated** | The identity provider meets it, see [D9](../decisions/d9-authentication-oidc-through-a-bff-ready-for-fapi-20.md). Axis asks for the `code` response type. |
| `V10.6.2` | Verify that the OpenID Provider mitigates denial of service through forced logout. By obtaining explicit confirmation from the end-user or, if present, validating parameters in the logout request (initiated by the relying party), such as the 'id_token_hint'. | **Delegated** | The identity provider meets it, see [D9](../decisions/d9-authentication-oidc-through-a-bff-ready-for-fapi-20.md). |
| `V10.7.1` | Verify that the authorization server ensures that the user consents to each authorization request. If the identity of the client cannot be assured, the authorization server must always explicitly prompt the user for consent. | **Delegated** | The identity provider meets it, see [D9](../decisions/d9-authentication-oidc-through-a-bff-ready-for-fapi-20.md). |
| `V10.7.2` | Verify that when the authorization server prompts for user consent, it presents sufficient and clear information about what is being consented to. When applicable, this should include the nature of the requested authorizations (typically based on scope, resource server, Rich Authorization Requests (RAR) authorization details), the identity of the authorized application, and the lifetime of these authorizations. | **Delegated** | The identity provider meets it, see [D9](../decisions/d9-authentication-oidc-through-a-bff-ready-for-fapi-20.md). |
| `V10.7.3` | Verify that the user can review, modify, and revoke consents which the user has granted through the authorization server. | **Delegated** | The identity provider meets it, see [D9](../decisions/d9-authentication-oidc-through-a-bff-ready-for-fapi-20.md). |
